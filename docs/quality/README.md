# 用户反馈验收：三个入口

本轮原文为 25 项反馈、29 张截图。原始 Word 只读；条目编号 FB-01～FB-25 按原文问题顺序，不沿用之前按修复批次命名的文档编号。

## 1. 看清单

`python scripts/acceptance.py status`

权威记录在 [feedback-ledger.json](feedback-ledger.json)，阅读版见 [feedback-ledger.md](feedback-ledger.md)。每项写清症状、验收条件、证据、版本和剩余限制。状态为 verified（约定范围已验证）、partial（部分通过）、open（明确未解决）、unverified（证据不足）。测试总数不能直接换算为反馈关闭数。

## 2. 跑固定检查

首次按项目 README 安装后端依赖、前端依赖和 Playwright Chromium。此入口不会自动安装依赖或读取/修改生产密钥。

`python scripts/acceptance.py local`

如果 Python/Node 不在常规位置，用 `--python 完整路径 --node 完整路径` 指定。默认本地端口 18480/13480，可用 `--backend-port`、`--frontend-port` 覆盖；入口不会占用或停止已有其他服务。

local 会运行工具自身的门槛测试、完整后端回归、前端 Webpack 生产构建和核心浏览器场景。后端使用独立临时 SQLite 和 Demo 模式，不调用真实文字模型。浏览器依赖 CDN 的导图库加载仍可能访问网络。局部调试可用 `--scope backend` 或 `--scope ui`；局部结果不等于完整验收。

报告写到 `.tmp/acceptance/<UTC时间>-local/report.json`；完整日志、截图与 trace 保存在同目录。只打印摘要；失败时读取相应日志。跳过、重试后才成功、零测试均不能算通过。报告不自动关闭问题，也不代表文字内容逐句正确。

## 3. 在线上固定版本验收

先按 AGENTS.md 测试、提交并推送本批改动，等服务器健康后取得完整 40 位提交号，再执行：

```text
python scripts/acceptance.py live --expected-commit <线上完整提交号> --identity <SSH私钥文件路径> --allow-live-models
```

如站点确实使用自签名证书，可为本次验收增加 `--allow-self-signed`；不改变用户浏览器和生产证书配置。默认主站 https://47.121.24.54，SSH root@47.121.24.54；其他部署可显式指定参数。

此模式会创建专用测试账号/书本，上传仓库内原创测试材料，并调用项目已配置的文字模型，产生正常服务用量。不会发送用户原始课件，不读取日常账号，不批量合成静态语音，不自动制作收费视频。样本链路包括六级问答/题目/闪卡/笔记、Word/PDF→课程→问答→B→笔记，以及金融、雅思、动画文件内容解析。它不是对所有原文件或所有模型输出的保证。

### 发布协调的实际机制

- 线上验收与现有 auto-deploy 共用 `/run/lock/sparklearn-auto-deploy.lock`。
- 先取得锁，再检查服务器部署提交；不匹配立即退出。验收期间自动部署定时器仍运行，但因锁被占用而跳过本次发布。
- 检查结束、异常退出或 SSH 连接关闭时释放；远端最长持有 1200 秒，最多可设 1800 秒。无需停掉 timer，也不会留下永久“暂停发布”状态。
- 锁丢失/到期使本轮验收失败。验收前后再检查健康接口的精确版本。
- 人工绕过 auto-deploy 的重启不受该锁保护；维护期间应避免手工重启。此机制协调发布，不等于实现零停机发布。
- 不并发运行多个同一生产站验收；每批只由一个任务负责推送与线上验收，其余任务先保留各自提交。

脚本用的是操作系统互斥锁，不是模型的口头约定。语义见 [flock 官方手册](https://man7.org/linux/man-pages/man1/flock.1.html)。

## 原创测试资料

`frontend/e2e/fixtures/` 内 Word/PDF 由本任务编写：生态学、CFA 术语、雅思词汇、五秒动画脚本。它们覆盖真实文件解析，但不冒充用户截图中的原件。不能仅以文件可上传就证明问答、互动音频和视频全部通过。

报告、trace、认证信息和生产原始返回保存在忽略目录，不提交。对外分享前应去掉会话、Cookie、认证头和其他账号数据。仓库内台账只保存无秘密值的结果摘要。

## 下一批怎样合作，少重复沟通

1. 先读台账，只挑同一原因的一组。每项保留原编号，避免修了一组却漏掉其中一个症状。
2. 只定位这组相关文件，先复现再改。修好后跑对应检查；准备统一发布时跑完整入口。
3. 一个批次统一提交发布，在线上固定版本跑真实流程；对音色、知识正确性、PPT 排版等仍查看实际成品。
4. 把结果和证据写回台账。下次从这份记录接着做，无须把整个聊天或所有源码重发给模型。

可以直接对 AI 说：

> 读取 docs/quality/feedback-ledger.json，按共同原因处理尚未关闭的问题。每次先给可复现证据，再做最小修复；复用 scripts/acceptance.py 的入口。只报有证据的结果，区分本地、线上和成品质量，最后更新台账。不要从头重查已经验证且未受影响的条目。

这套流程已写入项目 AGENTS.md，后续任务会自动看到。当前用仓库内脚本即可复用，无须为这一个项目另装 Skill。
