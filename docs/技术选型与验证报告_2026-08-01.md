# SparkLearn 技术选型与验证报告

日期：2026-08-01
范围：当前仓库、生产部署和本轮必要升级；不把课程示例原样搬进项目。

## 1. 一页结论

SparkLearn 不是“开发 Agent Teams 项目”，而是一个由 **FastAPI + LangGraph** 驱动的多智能体学习产品。课程最值得迁移的是“先调查、再做最小实验、最后用真实链路验收”的工程方法，不是把课程使用过的所有工具都装进项目。

本轮选型结论如下：

| 层级 | 采用方案 | 当前判断 |
| --- | --- | --- |
| Web 前端 | Next.js 16.2.12 + React 19.2.8 + Node.js 24 LTS | 保留 App Router 和 BFF，完成安全升级，不重写 Vite SPA |
| API 后端 | FastAPI + SQLAlchemy | 保留，和 Python AI/RAG 代码同语言，SSE 路径已存在 |
| 智能体运行时 | LangGraph `StateGraph` + 内置 `MiniGraph` 兜底 | 保留，当前确有条件路由、并行 fan-out/fan-in、状态 reducer 和事件流 |
| 文本模型 | 统一网关，讯飞星火 / DeepSeek 按部署配置选择，MockEngine 离线兜底 | 不把“代码支持”误写成“生产启用”；2026-08-01 生产实测为讯飞星火 X2 |
| RAG Embedding | FastEmbed 的中文 BGE 模型，哈希向量仅作兜底 | 保留，40 问基准通过；不以哈希兜底成绩冒充真实语义检索成绩 |
| 向量存储 | 当前单实例 MemoryStore；Milvus 保留为可选兼容路径 | 当前不启用额外集群；需要多实例或规模增长时优先评估 pgvector |
| 业务数据 | PostgreSQL + RLS；Redis 作缓存/任务基础设施 | 保留，注册、退出、重登和同一用户恢复已通过真实链路实验 |
| 部署 | 单台 ECS 上 Docker Compose + Nginx | 保留，符合当前规模和已有自动部署；不拆分到多个托管平台，不上 Kubernetes |
| Agent Teams | 不作为项目依赖 | 只在多个可独立工作的开发任务真正并行时临时使用 |
| LangChain 文档 MCP | 不作为业务运行时 | 它是获取官方文档的开发工具；项目运行不依赖它 |
| HITL / `interrupt` | 暂不增加 | 只有“高风险内容发布前必须等待教师批准”成为真实需求时再引入 |

## 2. 证据等级

为了防止“听说能用”被写成“已经能用”，本报告按以下等级判断：

1. **强证据**：当前生产接口、真实用户链路、自动化测试或生产构建直接观察到结果。
2. **中强证据**：仓库当前代码和配置明确存在，并能由局部实验验证。
3. **中等证据**：厂商官方文档说明能力存在，但本项目尚未实测。
4. **弱证据**：课程口述、搜索摘要、社区宣传或仅安装成功；只能形成候选，不能形成上线结论。

工程原则：**能力状态至少要分为“计划、已实现、已配置、生产实测”四层。**

## 3. 阶段一：先确认项目到底是什么

### 为什么这样调查

如果把“开发时多个 AI 协作”与“产品运行时多个 Agent 协作”混为一谈，会增加与用户价值无关的配置、文档和故障点。因此先读仓库入口、编排图、状态定义、部署文件和生产健康接口。

### 证据与强弱

- 强证据：`backend/app/agents/graph.py` 存在 LangGraph 条件路由与四资源节点并行；`state.py` 使用 reducer 合并并行结果。
- 强证据：本地真实链路经 BFF 完成注册、退出、重登、答疑 SSE，共收到 25 个事件并出现导师内容和 `done`。
- 强证据：生产 `/api/health` 在 2026-08-01 返回 `llm_provider=spark`，文本模型为讯飞星火 X2。
- 中强证据：代码包含 10 个业务智能体及离线 `MiniGraph` 兜底。

### 候选淘汰原因

- 淘汰“把 Agent Teams 写成项目必需依赖”：它优化开发分工，不负责学生画像、RAG 或学习路径运行。
- 淘汰“把 LangChain MCP 写进业务架构”：文档 MCP 提供规范检索，不执行 SparkLearn 的业务请求。
- 暂缓 HITL：当前核心路径是学生即时学习，不存在必须等待教师审批才能继续的明确产品阻塞点。

### 最小验证实验

运行 `deploy/verify-local-stack.ps1`，让一次请求穿过浏览器侧 BFF、认证、数据库和后端 SSE；同时故意提交伪造 `user_id`，确认 BFF 用登录身份覆盖它。

### 你应该学会的原则

**先画清“开发工具”和“产品运行时”的边界。工具名字相似，不代表它们属于同一层。**

## 4. 阶段二：前端与运行时

### 为什么这样调查

原仓库使用 Next.js 14 和 Node.js 20。版本老本身不是罪，但依赖审计出现高危/严重风险，Node.js 官方当前也已把 v20 标为 EOL，因此这是需要处理的真实风险。

### 证据与强弱

- 强证据：升级前 `npm audit --omit=dev` 报告 Next.js 相关高危/严重问题。
- 强证据：升级到 Next.js 16.2.12、React 19.2.8 后，干净安装、类型检查和生产构建通过，生产依赖审计为 0 个漏洞。
- 中等证据：[Next.js 16 官方升级指南](https://nextjs.org/docs/app/guides/upgrading/version-16)要求异步读取 route `params`，并要求 Node.js 20.9+、TypeScript 5+。
- 中等证据：[Node.js 官方发布状态](https://nodejs.org/en/about/previous-releases)显示 v24 为 LTS、v20 已 EOL；Docker Hub 已确认 `node:24.18.1-alpine` 标签有效。

### 候选淘汰原因

- 淘汰“继续留在 Next.js 14”：安全风险已有直接证据。
- 淘汰“改成 Vite SPA”：当前 Next.js route handler 承担认证 Cookie 和后端代理边界，重写收益小、回归面大。
- 淘汰“为了新而上 Node.js 26 Current”：生产应选择 LTS，不追逐 Current。
- 暂不改成独立前后端域名：会重新引入跨域、Cookie、部署和流式代理问题。

### 最小验证实验

依次执行 `npm ci`、`npm audit --omit=dev`、`npm run typecheck`、`npm run build`，再通过 Next.js BFF 跑注册和 SSE。只通过编译不足以证明 Cookie 与流式代理仍正常。

### 你应该学会的原则

**升级不是改版本号，而是“漏洞消失 + 编译通过 + 真实用户路径不退化”。**

## 5. 阶段三：后端与多智能体编排

### 为什么这样调查

需要判断 LangGraph 是实际解决问题，还是为了展示“多 Agent”而堆出来的框架。

### 证据与强弱

- 强证据：图中存在生成与答疑的条件分支，文档/脑图/题库/媒体并行执行，评估节点汇合。
- 中强证据：确定性规则优先，只有规则未命中才调用模型 `reasoner`，降低成本和不可预测性。
- 中等证据：[LangGraph 官方说明](https://docs.langchain.com/oss/python/langgraph/overview)把它定位为有状态、长运行工作流的低层编排运行时，支持 streaming、持久化和 HITL，也明确可以独立于 LangChain 使用。

### 候选淘汰原因

- 淘汰 CrewAI：更偏角色协作抽象，迁移会重写已通过验证的显式 DAG，当前没有可量化收益。
- 淘汰 LlamaIndex Workflows：它适合数据/RAG 工作流，但现有核心不仅是检索，还包含画像、路径、生成、评估和前端 AgentTrace 协议。
- 淘汰 Pydantic Graph 或完全自研图：会失去当前 LangGraph 生态能力，且 MiniGraph 已承担离线兜底。
- 淘汰“所有步骤都交给 LLM 自由决定”：学习路径、用户隔离和资源类型应优先确定性执行。

### 最小验证实验

后端全量 pytest 加一条流式答疑端到端测试；至少确认事件序列里有内容事件和结束事件，而不是仅检查 HTTP 200。

### 你应该学会的原则

**需要稳定的地方写规则，需要理解语言的地方用模型；Agent 的价值来自清晰责任和可观测状态，不来自数量。**

## 6. 阶段四：模型供应商

### 为什么这样调查

模型代码、密钥配置和线上实际选择可能不同。若不拆开，会产生“文档说 DeepSeek，线上却跑星火”的错误汇报。

### 证据与强弱

- 强证据：生产健康接口实测为讯飞星火 X2。
- 中强证据：`spark_client.py` 的统一网关支持 `spark`、`deepseek`、`auto` 和 MockEngine。
- 中等证据：供应商官方文档只能证明 API 存在，不能证明本项目密钥、额度、路由和响应质量已经验收。

### 候选淘汰原因

- 淘汰“只保留一个模型并删除适配层”：会损失离线演示与供应商故障切换能力。
- 淘汰“本轮强行切换 DeepSeek”：没有同题集、成本、延迟、grounding 质量的并行证据，且会改变生产付费路径。
- 淘汰“健康接口返回模型名就等于回答质量优秀”：配置可见性不是效果评测。

### 最小验证实验

使用固定题集分别记录回答成功率、引用正确率、首 token 延迟、总耗时与成本；只有同一输入、同一评分规则的 A/B 才能决定切换主模型。

### 你应该学会的原则

**供应商选择要靠任务级评测，不靠模型名气；“支持”不等于“已启用”，“已启用”不等于“效果最好”。**

## 7. 阶段五：RAG 与向量存储

### 为什么这样调查

课程容易让人产生“做 RAG 就必须上向量数据库”的印象。实际选型要看资料规模、并发、隔离、持久化和运维成本。

### 证据与强弱

- 强证据：40 问 RAG grounding 验收基准通过；运行时健康接口显示 BGE 中文 embedding，维度 512。
- 中强证据：生产 Compose 未配置 Milvus，当前代码因此使用可持久化 JSON 的 MemoryStore；检索会按 `user_id` 和 `source_id` 过滤。
- 中等证据：[pgvector 官方仓库](https://github.com/pgvector/pgvector)表明 PostgreSQL 可提供精确/近似向量检索；它与现有 PostgreSQL 共用备份和权限体系，适合作为下一阶段候选。

### 候选淘汰原因

- 当前不启用 Milvus：现有 Compose 方案需要 Milvus、etcd、MinIO 三个额外服务，超出当前小语料、单机部署的收益。
- 当前不新增 Qdrant：仍要增加一个需要备份和监控的服务，尚无规模证据。
- 当前不迁移 pgvector：方向合理，但需要迁移脚本、索引基准、租户过滤和回滚实验，不能只改依赖名。
- 哈希向量只保留故障兜底：它能证明管线可运行，不能代表语义检索质量。

### 最小验证实验

保留同一 40 问基准，把 MemoryStore 与 pgvector 候选在相同 embedding 下对比 Recall@k、引用正确率、p95 延迟、重启持久化和跨用户隔离。满足以下任一条件再启动迁移：

- 向量条目超过约 5,000，内存/JSON 重载开始影响启动或检索；
- 需要两个及以上后端实例共享同一向量索引；
- 上传资料持续增长，需要可靠备份、增量更新或运维观测。

### 你应该学会的原则

**先用指标触发复杂度，别用“架构看起来先进”触发复杂度。**

## 8. 阶段六：账号、数据与部署

### 为什么这样调查

教育产品的“个性化”只有在退出、重登和不同用户隔离后仍成立，才是真正的数据能力；页面能打开不是完成。

### 证据与强弱

- 强证据：本地注册 → `/auth/me` → 退出 → 登录 → `/auth/me` 返回同一用户 ID。
- 中强证据：生产使用 PostgreSQL，代码对用户数据表启用并强制 RLS。
- 中等证据：[PostgreSQL RLS 官方文档](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)说明启用 RLS 后，普通行访问必须由策略允许；无策略时默认拒绝。
- 中强证据：生产部署已经是 ECS + Compose + Nginx，Next.js 官方也支持 `next start` / Docker 自托管并建议在前面放反向代理：[自托管指南](https://nextjs.org/docs/app/guides/self-hosting)。

### 候选淘汰原因

- 淘汰“只做前端登录假象”：刷新或换设备后无法恢复个性化数据。
- 当前不把前后端拆分到不同托管平台：会增加跨域 Cookie、SSE、两处环境变量和两套故障域。
- 当前不上 Kubernetes：单机负载和团队规模没有证明它的运维成本值得。

### 最小验证实验

本地先跑真实账号链路；推送后等待 ECS 自动部署，再在生产重复健康、首页、注册、退出、重登、身份恢复和短答疑 SSE。部署记录必须包含 Git SHA、时间、线上 URL 与结果。

### 你应该学会的原则

**技术上线的完成定义是“真实用户路径在真实环境可用”，不是进程存在、健康接口 200 或脚本退出码为 0。**

## 9. 课程方法如何选择性迁移

| 课程内容 | 对 SparkLearn 是否有用 | 正确用法 |
| --- | --- | --- |
| 先技术调研再编码 | 有用 | 只调查会影响当前决策的候选，并写退出条件 |
| 规范文档 | 有用 | 记录当前事实、证据等级、运行命令和验收口径 |
| Agent Teams | 条件有用 | 仅当任务可独立并行且合并边界清晰时使用，不进入业务依赖 |
| LangChain 文档 MCP | 条件有用 | 查询官方最新规范；不是 SparkLearn 后端，也不证明 MCP 业务接入成功 |
| LangGraph `interrupt` / HITL | 未来可能有用 | 教师审核高风险内容、发布前批准、人工修订后恢复执行 |
| “Interpreter” | 不采用该说法 | 课程语音误识别；此处相关概念是 `interrupt`，与代码解释器不是一回事 |

明确结论：**LangChain 的文档 MCP 主要负责获取官方最新的文档规范，不等于业务运行时本身。** 当前没有把它写入仓库配置，因为 SparkLearn 的构建和线上运行都不依赖它。

## 10. 风险、退出条件与下一步

| 风险 | 当前控制 | 何时重新选型 |
| --- | --- | --- |
| Next.js 传递依赖再次出现安全告警 | 锁文件、生产依赖审计、固定 Docker Node LTS | 审计重新出现 high/critical，或 override 已被上游修复可删除 |
| Python 依赖使用宽松范围导致漂移 | 当前全量测试与生产镜像构建把关 | 出现不可复现部署时，引入受审计的锁文件，不做盲目全量升级 |
| MemoryStore 单机限制 | 40 问基准、持久化和租户过滤 | 超过规模/多实例阈值时先做 pgvector 对照实验 |
| 模型供应商文档与生产事实不一致 | 健康接口和能力状态表 | 每次切换供应商后更新实测日期和固定题集结果 |
| HITL 缺失 | 当前没有强制审批需求 | 教师发布、敏感内容或高风险操作出现明确审批责任时引入 `interrupt` |

本轮完成标准：

- 前端生产依赖审计无漏洞，类型检查和生产构建通过；
- 后端全量回归通过；
- 本地真实账号与答疑 SSE 通过；
- 只提交本任务文件并推送 `origin/main`；
- ECS 自动部署到同一 Git SHA；
- 生产健康、首页、账号恢复和答疑 SSE 通过。

这份报告不是永久真理。它是一张“基于 2026-08-01 证据做出的决策快照”；当规模、需求或实测数据变化时，应按退出条件重新调查。
