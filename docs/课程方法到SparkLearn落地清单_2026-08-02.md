## 1. 最重要的判断

课程和 SparkLearn 都属于 Agent 应用工程，但不是同一个产品：课程项目是“智能文档审核”，SparkLearn 是“个性化学习”。因此应该迁移课程的工程方法，不应照搬它的全部页面、审批链和工具配置。

课程里最值得迁移的一句话是：**先证明每个组件单独成立，再写清接口关系，最后用真实运行、联调和部署证据把它提升为产品。**

## 2. 课程方法怎样落到当前项目

| 课程方法 | SparkLearn 当前证据 | 本轮动作 | 为什么 |
| --- | --- | --- | --- |
| 环境和能力先校准 | 已有 `AGENTS.md`；但 LangChain MCP 与 HITL 边界没有独立 setup 记录 | 新增环境校准文档，并真实查询 LangChain 官方 MCP | 防止把“能看到工具”误写成“项目依赖/功能已实现” |
| 需求驱动选型 | 现有 API/后端测试较强，缺少真实浏览器按钮与页面状态证据 | 选择 Playwright，而不是继续只写接口脚本 | 工具要填证据缺口，不按流行度选择 |
| 单组件 MVP | 全功能浏览器测试一次铺开会脆弱、难定位 | 先覆盖注册 → 提问 → 回答 → 刷新 → 退出重登 | 一条最核心链路先闭环，失败时能定位 |
| 环境隔离 | 生产有真实账户和模型费用 | 本地测试使用独立端口、独立 SQLite、演示模型和测试账户 | 自动化测试不能污染生产数据或产生不必要费用 |
| 接口契约先行 | Next.js BFF 和 FastAPI 已真实联调 | 浏览器测试继续走真实 BFF，不拦截、不伪造 API | 页面通过不应建立在 Mock 假象上 |
| 运行结果高于文档 | 原测试主要证明 API/SSE，不证明 DOM 和按钮 | 真跑 Chromium，并保留失败 trace/截图/视频 | “装好了”与“用户能用”是两回事 |
| 部署才算交付 | 项目固定由 GitHub 推送触发 ECS 部署 | 提交、推送、等待部署后再跑生产用户链路 | 本地成功不能代表线上镜像和代理正常 |
| 自动化 + 人工复核 | 课程强调最终验收要有界面证据 | 自动回归外，再提供人工走查清单 | 自动化擅长重复，人工擅长感受文案、节奏和视觉 |

## 3. 本轮明确不照搬的内容

| 候选 | 当前不采用原因 | 重新评估触发条件 |
| --- | --- | --- |
| 全程 Agent Teams | 修改范围集中，并行协作的沟通/合并成本高于收益 | 有两个以上独立模块、不同文件边界和独立验收 |
| 把 LangChain MCP 接入业务后端 | MCP 是官方文档检索工具，不负责线上学习请求 | 只有产品真的需要“业务 MCP”时另做协议与安全设计 |
| 立即实现教师 HITL | 当前学生学习是即时反馈，没有必须等待教师审批的阻塞点 | 教材发布、敏感内容或高风险操作被明确要求人工批准 |
| 新建教师管理端 | 没有教师角色、权限、审核对象和审计需求，先建会成为空壳页面 | 产品需求明确四件事后：谁审批、审什么、如何决策、怎样追责 |
| 照课程切换 ChatOpenAI + DeepSeek | SparkLearn 已有统一模型网关，生产当前走讯飞星火；盲目替换会破坏已验证链路 | 用同一题集证明质量、成本或延迟有可量化收益 |
| 重做 Figma/前端 | 当前缺口是验收证据，不是没有页面 | 用户研究或可用性测试发现明确交互问题后 |

## 4. 为什么本轮选 Playwright

### 调查原因

现有 PowerShell 端到端脚本能证明 BFF、认证、数据库和 SSE 能通，但它看不到“创建账户按钮能否点击”“回答是否真的显示在页面”“刷新后界面是否仍是登录状态”。这就是本轮证据缺口。

### 证据强弱

- 强证据：仓库里已有 API/后端测试，但此前没有浏览器 E2E 配置和用例。
- 中强证据：Playwright 官方提供测试运行器、浏览器隔离、用户可见定位器、自动启动 Web 服务以及失败 trace。
- 弱证据：课程说要做真实联调。它能决定原则，不能单独证明 Playwright 最适合本仓库。

### 候选淘汰

- 只扩展 PowerShell 接口脚本：仍看不到 DOM、按钮和页面状态，不能补缺口。
- Selenium：能完成任务，但当前前端是 TypeScript/Next.js，Playwright 的测试运行器、自动等待和失败产物更贴合，额外装配更少。
- 只靠人工点页面：适合体验检查，但难以每次发布稳定重复，也难形成回归门禁。

### 最小实验

让真实 Chromium 完成一次：创建隔离账户 → 发出学习问题 → 页面出现非空学伴回答 → 刷新仍保持登录 → 退出 → 同一账户重新登录。

### 工程原则

**选型不是问“哪个工具最好”，而是问“当前最缺哪种证据，哪个工具能用最小成本补上”。**

## 5. 自动测试和人工测试怎样配合

自动化负责每次都一样的问题：按钮存在、请求成功、状态恢复、核心文字出现。人工负责难写成稳定断言的问题：页面是否好懂、动画是否太慢、回答是否真的适合初学者、移动端是否舒服。

本轮 AI 可以完成自动化和辅助视觉检查，但不能冒充真实学生的主观体验。最终仍建议你亲手完成一次五分钟走查，并把不理解或不舒服的地方记成问题。

## 6. 本轮实测怎样校正了实现

| 实测现象 | 真正原因 | 修正 | 学到什么 |
| --- | --- | --- | --- |
| 首次运行停在“正在恢复你的学习空间” | Next.js 开发服务器拒绝 `127.0.0.1` 的开发资源来源 | 本地浏览器入口改用 `localhost`，不放宽生产安全配置 | 失败先看运行证据，不要立刻改选择器 |
| “开始学习”定位出现两个匹配项 | 页面有一个聚焦输入框按钮和一个真正提交按钮，名称相同 | 使用明确的 `aria-label` 定位提交按钮 | 不用 `.first()` 掩盖歧义，选择器应表达用户意图 |
| 注册和回答成功，但刷新后变成“演示同学” | `DEMO_MODE=true` 同时关闭认证，旧脚本把两个 `demo_user` 相等误判为账户恢复 | 允许 `AUTH_REQUIRED=true` 在演示模型下独立开启；新增配置单测和真实账户断言 | 离线模型与假账号是两件事；断言要证明业务含义 |

最终本地证据：

- Chromium E2E：1/1 通过，覆盖注册、页面答疑、刷新身份、退出和重登；
- 后端回归：237/237 通过；
- 前端生产依赖审计：0 个漏洞；
- TypeScript 类型检查与 Next.js 生产构建：通过；
- 原有 BFF/API/SSE 验收：真实账户、同一用户重登、25 个 SSE 事件、tutor 内容和 `done` 均通过。

以上属于强证据，因为来自当前仓库的真实运行结果；Playwright 官方文档和课程方法属于选型依据，强度低于项目实测。

## 7. 面试时可以这样讲

> 我没有因为项目叫多智能体，就把 Agent Teams、MCP、HITL 全部堆进去。我先检查真实运行架构和测试证据，发现后端、接口和 SSE 已有验证，但浏览器页面主链路缺少自动回归。因此我用 Playwright 做了一个隔离的最小闭环，覆盖注册、提问、回答、刷新会话和重新登录；再推送到 ECS 重复真实用户路径。LangChain 文档 MCP 只在遇到 LangGraph 最新 API 不确定时查官方规范，不进入生产链路。这个过程体现的是需求驱动选型、证据分级、最小实验和真实交付，而不是堆工具名。
