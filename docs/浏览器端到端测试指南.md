# SparkLearn 浏览器端到端测试指南

## 1. 它是什么

把 Playwright 想成一个“不会嫌烦的机器人学生”。它打开真正的 Chromium 浏览器，像用户一样点按钮、填邮箱、发问题，并检查页面上是否真的出现结果。

这和只测后端的区别是：后端测试像检查厨房能不能出菜；浏览器端到端测试像顾客从进门、点餐到真正吃到菜。

## 2. 当前自动覆盖的学生链路

测试文件：`frontend/e2e/learning-flow.spec.ts`

1. 创建一个随机且隔离的测试账户；
2. 从首页输入“请用一句话解释二叉树。”；
3. 通过真实 Next.js BFF 请求 FastAPI；
4. 确认学习对话里出现用户问题和非空学伴回答；
5. 刷新页面，确认登录 Cookie 仍有效；
6. 退出，再用同一邮箱和密码登录。

本地执行时会自动启动前后端，使用独立 SQLite 数据库、真实认证和演示模型，不读取真实模型密钥，也不会污染常用数据库。这里特意把“模型是否离线”和“登录是否真实”拆成两个开关，避免演示回答掩盖账户持久化问题。

## 3. 第一次怎样运行

在 PowerShell 中执行：

```powershell
cd C:\Users\26054\Desktop\sparklearn-multiagent\frontend
npm install
npm run test:e2e:install
npm run test:e2e
```

常用命令：

```powershell
npm run test:e2e          # 无界面快速回归
npm run test:e2e:headed   # 看见浏览器自动操作
npm run test:e2e:ui       # 打开 Playwright 调试界面
```

测试生产环境时，PowerShell 可以临时指定网址：

```powershell
$env:PLAYWRIGHT_BASE_URL="https://47.76.129.100"
npm run test:e2e
Remove-Item Env:PLAYWRIGHT_BASE_URL
```

生产测试会创建一个 `@example.test` 测试账户并调用真实模型，只在发布验收时运行，不要高频执行。

## 4. 测试失败时先看什么

不要先判断“Playwright 坏了”，按用户旅程定位：

1. 注册失败：看认证接口、Cookie 和数据库；
2. 进入不了学习页：看前端状态和 BFF；
3. 用户问题出现但没有回答：看 SSE、模型/演示模式和前端事件处理；
4. 刷新后退出：看 Cookie 持久化与 `/auth/me`；
5. 重新登录失败：看密码哈希与账户持久化。

失败产物默认在：

- `frontend/test-results/`：trace、截图、视频等失败证据；
- `frontend/playwright-report/`：HTML 报告。

## 5. 它能证明什么，不能证明什么

能证明：在被测环境和浏览器中，核心学生链路按预期运行，前端、BFF、认证、数据库和后端答疑能协同工作。

不能证明：所有浏览器和手机都无问题、答案教学质量一定优秀、系统没有安全漏洞、真实高并发一定稳定。因此还需要单元测试、接口测试、安全检查、性能测试和人工体验走查。

## 6. 你的五分钟人工走查

- [ ] 第一次打开页面时，我能在 10 秒内明白怎样开始学习。
- [ ] 注册、登录、退出的文案没有让我困惑。
- [ ] 提问后等待过程有反馈，不像页面卡死。
- [ ] 回答对零基础学生看得懂，不只是技术上“有文字”。
- [ ] 刷新和重新登录后，我仍能认出这是自己的账户。

## 7. 你应该学会的工程原则

1. 端到端不是“前端测试”的别名，而是从用户入口穿过所有关键层直到结果出现。
2. 自动化测试关注可重复事实，人工测试关注理解、信任和体验，两者互补。
3. 测试数据要隔离；能在本地用演示模型验证的，不要浪费生产费用。
4. 第一个 E2E 不求覆盖所有页面，先守住最重要、最容易影响用户的一条链路。
5. 失败截图和 trace 不是附属品，而是帮助团队复现问题的证据。
